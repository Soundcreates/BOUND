# Arkiv read boundary

`createArkivRpcReader` queries a configured HTTPS RPC for watcher-owned records. It verifies the chain ID (Rabdi 7794095 by default), filters `$owner` and a configured schema tag, keyset-paginates, checks response owner, schema, expiry and record shape, and rejects a page set spanning multiple blocks instead of returning a partial bundle. This strict block policy may require retries on a busy chain. `queryBundle` performs the additional owner and expiry checks using the caller's current block. A schema tag is not authentication.

The reader's **proposed** entity representation uses an `arkiv.schema` string and a `payload` bytes attribute containing UTF-8 JSON. Arkiv strings are limited to 128 UTF-8 bytes, so a JSON record must not be stored in a single `str` attribute. The bytes field supports up to 128 KiB. Payload attributes, tags and write encoding still need agreement and a funded live write/read/expiry test; this reader has not been validated against a BOUND-written entity. See [Arkiv's limits](https://docs.arkiv.network/reference/limits/) and [read API](https://docs.arkiv.network/json-rpc/querying-data/).

The owner-wide query is appropriate for the bundled watcher download. It is not a per-site query implementation and does not provide Anon-RPC. No direct per-site or sensitive client lookup should be added here as a fallback. The optional access key is sent in the `x-api-key` header and is not included in error messages. Never commit keys.

On 2026-11-06 an unauthenticated public Rabdi query for the zero address and `bound.record.v1` returned zero records after the reader verified chain 7794095. This confirms a read path and query syntax only; it does not prove writer ownership, expiry, pagination consistency over a real populated dataset, or integration with the extension.

`sender.js` provides a single-process transaction-journal boundary for an injected signer, transaction decoder, ABI codec, chain client, broadcast and confirmed-receipt/entity reader. It persists signed bytes before broadcast and retries the same transaction after uncertain submission. Before acknowledging, it requires a matching transaction hash, watcher owner, unexpired entity, and matching record. A wrong chain, destination, signer, value, calldata, or conflicting operation ID fails closed. The configured Arkiv contract address must be independently verified on the selected chain before use; this module does not discover or verify deployment bytecode. The injected transaction decoder must cryptographically recover the signer, and the receipt reader must validate the real receipt and entity metadata. These adapters are not yet implemented or live-tested. Pending/reverted transactions require operational reconciliation; no replacement transaction is generated automatically. Signed transaction journals contain public-but-not-yet-published observations and must stay in a private, ignored location. This is not a claim of exactly-once behavior across multiple writers or processes.

`writer.js` adds an idempotent record boundary: it requires an operation-ID lookup, creates only when no prior record exists, and acknowledges only after a public read-back matches the configured owner, payload and expiry. The caller's SDK adapter must store the operation ID as an indexed field, write the schema tag and payload, sign on Rabdi, and return the actual Arkiv metadata. Its contract tests use fakes and do not submit transactions.

`codec.js` encodes the proposed named schema, indexed record kind and operation ID, and bytes payload as one Arkiv create operation. Its salt is deterministically derived from the operation ID so rebuilding the same transaction data is stable. Use a random operation ID and a configured lifetime; the codec does not manage nonce, signature, transaction fees, status updates, or storage. On 2026-11-06 a read-only `eth_call` on Rabdi accepted a synthetic create payload produced by this codec and rejected a truncated `execute` call. Reproduce with `scripts/integration/arkiv-call-smoke.mjs`, supplying an HTTPS Rabdi RPC and the system address from the [official Arkiv write documentation](https://docs.arkiv.network/json-rpc/mutating-entities/). The call persists nothing and is not a live-write or receipt test.

The documented system address `0x4400000000000000000000000000000000000044` returned `0x` from `eth_getCode` on Rabdi, while its documented `entityNonce` call returned a 32-byte zero and the malformed `execute` call reverted. This is consistent with a native system implementation, but no deployed bytecode was verified. The plan's `cast code` verification rule cannot be claimed as satisfied; reconcile that requirement with the network's native system contract semantics before configuring the address for a live writer. `cast` is not installed in this checkout.

The codec also builds a patch for a previously verified entity key. The caller must verify the existing entity's owner, kind, and expiry before patching; the codec does not extend expiry or ensure status transition ordering. A Rabdi `eth_call` to patch a synthetic nonexistent key returned the documented `EntityNotFound(bytes32)` selector, showing that the request reached the patch handler without persisting data. A real owner-authorized patch and expiration/extension still require a funded live test.
